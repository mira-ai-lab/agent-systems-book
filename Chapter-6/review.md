# Chapter 6 代码 Review 规范与检查清单

> 本文同时作为 Chapter 6 本轮 Review 的结论记录，以及后续章节可复用的 Review 模板。

## 1. Review 目标

Chapter 6 的代码应满足以下目标：

1. 章节主题聚焦 **领域智能体角色设定、任务与智能体匹配、中心化编排**。
2. 保留“一个中心控制器完成任务拆解、依赖排序并调度领域智能体”的架构。
3. 明确复用 Chapter 2、3、4、5 的能力，避免重复实现。
4. 保持模块职责单一、调用链清晰、代码精简，删除无实际调用的功能。
5. Notebook 应体现完整教学过程，并保证所有代码单元能够实际运行。

## 2. 必须保留的架构边界

### 2.1 中心化编排

- 只保留中心化编排模式。
- 不保留顺序编排、固定图或无关的 Supervisor 示例。
- 中心控制器负责：
  1. 判断请求是否属于旅行任务。
  2. 组织任务规划、依赖分析、智能体路由和领域智能体执行。
  3. 收集并选择最终旅行规划结果。
- 后续步骤由代码显式控制，不把完整执行过程交给单个中心大模型自由发挥。

### 2.2 模块职责

| 模块 | 应负责 | 不应负责 |
|---|---|---|
| `task_plan.py` | 事实调查、任务拆解、依赖分析、执行顺序 | 智能体路由 |
| `agent_routing.py` | 子任务到领域智能体的匹配、工具参数提取 | 任务拆解、依赖推断 |
| `orchestrator.py` | 请求分诊、流程控制、分层执行、最终结果选择 | 重复实现任务规划或领域搜索 |
| `domain_agents.py` | 智能体定义、工具、能力目录、实例创建 | 中心调度 |
| `memory_adapter.py` | 适配 Chapter 3 的记忆能力 | 重新实现记忆存储和检索 |
| `config.py` | 路径、环境变量和跨章导入 | 业务逻辑 |

### 2.3 不保留的旧结构

- `central_orchestrator.py` 应统一为 `orchestrator.py`。
- `TaskPlanner`、`task_planner.py` 改为 `task_plan.py`，避免职责和命名含混。
- `agent_routing.py` 必须独立保留，不能重新合并到任务规划模块。
- 删除 `fixed_graph/`、无关 Supervisor、独立聚合智能体、`travel_planning.py`、
  `aggregation_helpers.py`、`execution_helpers.py`、`travel_common.py` 和无调用价值的辅助层。

## 3. 任务规划与依赖分析

### 3.1 Chapter 4 复用原则

- 任务拆解和依赖分析属于 Chapter 4 已讲内容。
- 可复用的任务拆解、依赖分析与拓扑排序逻辑应放在 Chapter 4 的独立模块中。
- Chapter 4 Notebook 保持原有“基于能力”的教学方式，不直接导入面向 Chapter 6 的模块。
- Chapter 6 直接导入 Chapter 4 的依赖分析实现，不允许维护第二份不一致逻辑。

### 3.2 任务拆解提示词

- 任务拆解提示词拆分：
  - `TASK_DECOMPOSITION_SYSTEM_PROMPT`
  - `TASK_DECOMPOSITION_USER_PROMPT`
- System Prompt 负责：
  - 角色定义。
  - 职责边界。
  - 可用能力目录。
  - 子任务拆解原则。
  - 输出格式。
  - 禁止输出智能体名称或执行主体。
- User Prompt 只负责：
  - 背景信息。
  - 用户输入。
  - 要求遵循 System Prompt。
- 能力目录放在 System Prompt 中，不放在 User Prompt 中。

### 3.3 子任务要求

- 子任务只描述要完成的业务工作。
- 子任务不得出现：
  - 智能体名称。
  - `Agent` 后缀。
  - “使用某智能体”“由某智能体执行”等执行主体说明。
- 该约束通过提示词解决，不允许增加正则清洗等后处理补丁。
- 每个子任务应包含足够槽位信息，并追求最少且完整的任务数量。

### 3.4 依赖关系

- 依赖分析依据任务输入与候选能力输出定义。
- 没有明确依赖时，不进行多余重排。
- 依赖图必须经过拓扑顺序校验。
- Chapter 6 不重新定义“最终回复智能体”标记；最终顺序由任务规划和依赖结果决定。

## 4. 智能体路由

- `agent_routing.py` 保持独立模块。
- 路由输入包括：
  - 领域智能体及技能目录。
  - 事实调查结果。
  - 已拆解任务。
  - 本地验证后的依赖关系。
- 路由模型内部可使用 JSON 作为控制结构。
- 路由输出必须经过本地校验：
  - 智能体名称必须存在。
  - 工具参数字段必须属于该智能体。
  - 任务原文和依赖关系由本地代码保留，不能由模型任意修改。
- 下发给领域智能体的是自然语言子任务，不是路由模块原始 JSON。
- 存在依赖时，当前领域智能体只接收：
  - 前序子任务。
  - 前序任务下发的领域智能体。
  - 该领域智能体的回复。
- 工具原始结果不向下游继续传递。
- Notebook 中应展示路由提示词和“子任务 → 领域智能体”结果，而不是打印参数字典。

## 5. 中心智能体与 System Prompt

- 中心智能体需要自己的 System Prompt。
- 中心 Prompt 的首要职责是请求分诊：
  - 旅行规划及旅行领域查询进入多智能体流程。
  - 非旅行任务直接由模型回答，不启动复杂调度。
- 中心 Prompt 不重复 Task Plan 已有的预调查、任务拆解和依赖分析指令。
- 中心 Prompt 不硬编码领域智能体列表。
- 中心 Prompt 不负责重新选择智能体，智能体选择由独立路由模块完成。
- 中心 Prompt 和流程控制需要使用英文注释说明：
  - 先说明当前步骤的关键能力。
  - 再说明复用了哪个章节的能力。

## 6. 领域智能体定义

### 6.1 定义方式

- 使用 `AgentSpec` 统一声明：
  - `name`
  - `description`
  - `tools`
  - `system_prompt`
  - `input_fields`
  - `output_fields`
  - `parallel_safe`
- 使用 `ToolSpec` 声明工具、参数和返回字段。
- 使用 `DOMAIN_AGENT_SPECS` 作为唯一定义源。
- 不应同时保留 `AgentSpec` 和另一套重复的智能体工厂定义。
- 智能体实例使用缓存创建函数即可，不额外保留 `SubAgentFactory`。

### 6.2 智能体描述

- 描述应说明“输入对象 + 推荐/查询动作 + 单次调用边界”。
- 不使用 POI 等对读者不友好的术语，优先使用自然语言。
- 当前 Chapter 6 的六个领域智能体：
  - `WeatherAgent`
  - `AttractionAgent`
  - `HotelAgent`
  - `RestaurantAgent`
  - `FlightAgent`
  - `ItineraryAgent`
- 描述应能直接用于任务拆解和智能体匹配，不应把工具实现细节写进职责描述。

### 6.3 提示词与工具

- 智能体描述说明角色能力。
- 工具 Docstring 和 Schema 说明参数、约束和返回结构。
- 智能体 System Prompt 不应重复教授工具参数填写方式，应依赖工具描述和 Schema。
- 工具结果为空时，智能体必须如实说明，不得补造事实。
- `ItineraryAgent`：
  - 不调用领域工具。
  - 消费前序智能体结果。
  - 是最终日程规划与总结的唯一角色。
- 不保留独立总结/聚合智能体，也不保留 `AggregationAgent`。

## 7. Chapter 6 工具边界

- Chapter 6 不涉及 MCP 工具调用。
- 不保留飞常准、Aviationstack 等未使用或未讲解的 MCP/HTTP 接口。
- 天气工具直接返回空结果，并说明后续章节补充。
- 航班工具直接返回空结果，并说明后续章节补充。
- 不保留 `synthetic_weather_by_city_and_date` 等伪实现。
- 不保留无实际调用的城市提取、城市校验、餐馆分类归一化等辅助函数。

## 8. 长期记忆与共享 LLM

- 长期记忆直接复用 Chapter 3。
- 通过 `memory_adapter.py` 做章节适配，不新增冗余 `Chapter3MemoryService`。
- 不增加无必要的 `_async_json_chat` 等重复封装。
- 同步/异步记忆能力不足时，优先在 Chapter 3 补齐对应方法。
- 大模型访问统一放在仓库根目录 `llm.py`。
- 定期检查功能重复的 LLM 调用函数并进行合并。

## 9. 日期处理

- 删除 Chapter 6 独立的 `date_context.py`。
- 不保留日期锚点、日期正则和时间兜底系统。
- 相对日期转换由事实调查 Prompt 完成：
  - 使用当前日期。
  - 将“今天、明天、下周”等转换为 `YYYY-MM-DD`。
  - 不额外增加 `trip_dates` 字段。
- 领域工具接收事实调查阶段换算后的确切日期。

## 10. Notebook 教学要求

### 10.1 入口顺序

Chapter 6 入口 Notebook 建议保持以下顺序：

1. 环境与模块导入。
2. 领域智能体角色定义，打印数量、名称、职责、工具、输入输出和提示词摘要。
3. 用户旅行规划问题。
4. 中心 System Prompt 与请求分诊。
5. 事实调查与长期记忆检索。
6. 任务拆解与依赖分析（合并演示）。
7. 智能体路由提示词。
8. 智能体路由执行与结果。
9. 领域智能体执行结果。
10. 最终旅行规划。
11. 非旅行请求直答对比。
12. 小结。

### 10.2 教学表达

- 第一部分先介绍领域智能体角色定义，不演示单独调用单个智能体。
- 说明“定义了 6 个领域智能体、分别是什么、定义在哪个文件”。
- Chapter 4 已讲过的任务拆解与依赖分析不要重复展开，合并为少量单元格并指向 Chapter 4。
- 每个关键步骤至少显式调用对应函数，再输出结果。
- 智能体路由部分需要展开：
  - 展示路由 Prompt。
  - 说明输入结构。
  - 打印“子任务 → 领域智能体”结果。
- 不把路由内部 JSON 当成下发给领域智能体的内容。
- 存在依赖时，展示实际传给下游智能体的前序任务、智能体和回复。
- 学习重点固定为：
  - 领域智能体角色设定。
  - 任务与智能体角色匹配。
  - 中心化编排。

### 10.3 Notebook 稳定性

- 修改后必须实际执行。
- 所有代码单元应有执行计数，不应有错误输出。
- Cursor 等外部编辑器可能覆盖磁盘文件；执行前应关闭或刷新旧标签页。
- 执行完成后必须重新检查标题、说明、关键代码块和输出是否仍在。

## 11. 代码质量与文档

- 文件职责应高内聚、低耦合。
- 不创建大量职责不清的 `_helper.py`。
- 删除无调用方代码前先搜索整个仓库。
- 避免为很短的逻辑增加冗余小函数。
- 不要使用 `require_non_empty` 这类低价值通用校验函数。
- 模块级 Docstring 应说明：
  - 文件整体能力。
  - 主要职责。
  - 输入输出或模块边界。
  - 作者。
  - 日期。
- 关键函数 Docstring 应说明：
  - 能力。
  - 入参。
  - 出参。
  - 异常或失败行为。
- `orchestrator.py` 的流程注释使用英文，先写关键能力，再补充复用的章节能力。

- 未经确认不 push 远程分支。
- 提交前确认：

  - 没有密钥。
